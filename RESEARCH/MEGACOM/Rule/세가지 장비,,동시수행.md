현재 업로드한 4개 Python 파일을 확인했습니다. **R00012, R00047, R00048 세 장비에 대해 RULE, CF, LSTM을 모두 실행하도록 변경할 수 있습니다.**

현재는 rule.py와 cf.py에 R00012가 고정되어 있고, lstm_predict.py는 실행 인자로 장비를 지정하도록 되어 있습니다.

## 1. 변경할 장비

DEVICE_IDS = ["R00012", "R00047", "R00048"]

|분석 프로그램|현재|변경|
|---|---|---|
|RULE|R00012|3개 장비|
|CF|R00012|3개 장비|
|LSTM|GUI에서 지정한 1개 장비|3개 장비|
|데이터 조회|장비별|장비별 독립 조회|
|DB 저장|장비별|장비별 독립 저장|
|실행 주기|5초|5초|

## 2. RULE 수정

현재 rule.py에는 다음 설정이 있습니다.

DEVICE_ID = "R00012"

이를 실행 인자로 지정할 수 있도록 변경하는 것이 좋습니다.

DEVICE_IDS = ["R00012", "R00047", "R00048"]

다만 단순히 상수를 리스트로 변경하면 기존 SQL과 저장 코드가 작동하지 않습니다. 현재 RULE 코드의 조회·저장 함수들은 단일 DEVICE_ID를 사용하므로 장비별 반복 실행 구조로 변경해야 합니다.

## 3. CF 수정

현재 cf.py에서도 다음과 같이 장비가 고정되어 있습니다.

DEVICE_ID = "R00012"

CF에서는 recent_rows(), last_predictions(), prediction_rows(), update_actual_temperatures() 등이 이 값을 사용합니다.

따라서 장비별로 다음 순서가 수행되도록 수정해야 합니다.

`CF 실행 │ ├── R00012 │ ├── 최신 데이터 조회 │ ├── 10/30/60/120분 예측 │ └── ai_oiltemp 저장 │ ├── R00047 │ ├── 최신 데이터 조회 │ ├── 10/30/60/120분 예측 │ └── ai_oiltemp 저장 │ └── R00048 ├── 최신 데이터 조회 ├── 10/30/60/120분 예측 └── ai_oiltemp 저장`

**주의:** 현재 CF 모델은 R00012 전용으로 학습된 모델입니다. 다른 두 장비에도 적용할 수는 있지만, 예측 정확도를 검증해야 합니다.

## 4. LSTM 수정

현재 lstm_predict.py는 다음 인자를 받습니다.

parser.add_argument("--comcode", default=COMCODE)

parser.add_argument("--device-id", default=DEVICE_ID)

따라서 LSTM은 장비별 프로세스를 실행하는 방식으로 변경할 수 있습니다.

예를 들어:

```
python lstm_predict.py --interval 5 --comcode C00088 --device-id R00012
python lstm_predict.py --interval 5 --comcode C00088 --device-id R00047
python lstm_predict.py --interval 5 --comcode C00088 --device-id R00048
```

각 프로세스는 자기 장비의 센서 데이터를 조회하고 ai_lstm_r에 결과를 저장합니다.

단, LSTM 역시 R00012 학습 모델을 다른 장비에 그대로 적용할 경우 성능 검증이 필요합니다.

## 5. GUI 수정

현재 main.py는 RULE, CF, LSTM 각각 하나의 프로세스를 관리합니다.

이를 다음과 같이 변경하는 것을 권장합니다.

DEVICE_IDS = ["R00012", "R00047", "R00048"]

GUI의 실행 버튼을 누르면 각 장비에 대해 독립적인 프로세스를 시작합니다.

`MEGACOM GUI │ ├── RULE 시작 │ ├── R00012 │ ├── R00047 │ └── R00048 │ ├── CF 시작 │ ├── R00012 │ ├── R00047 │ └── R00048 │ └── LSTM 시작 ├── R00012 ├── R00047 └── R00048`

이 구조에서는 총 9개 프로세스가 실행됩니다.

장점은 특정 장비에서 센서 결측이나 예측 오류가 발생하더라도 다른 장비의 처리를 계속할 수 있다는 것입니다.

다만 DB 연결 수와 메모리 사용량이 증가합니다. 특히 LSTM 모델을 세 프로세스에서 각각 로딩하므로 메모리 사용량을 확인해야 합니다.

## 6. 권장 구현 방식

저는 **프로세스를 9개 실행하는 방식보다 RULE, CF, LSTM 각각 하나의 프로세스에서 3개 장비를 순차 처리하는 방식**을 우선 권장합니다.

`MEGACOM GUI │ ├── RULE (1개 프로세스) │ └── R00012 → R00047 → R00048 │ ├── CF (1개 프로세스) │ └── R00012 → R00047 → R00048 │ └── LSTM (1개 프로세스) └── R00012 → R00047 → R00048`

이렇게 하면 기존 GUI의 시작·중지 버튼을 그대로 사용할 수 있고, LSTM 모델을 한 번만 로딩할 수 있습니다.

장비별 오류를 독립적으로 처리하고, 마지막 처리 시각도 장비별로 관리해야 합니다. 특히 LSTM의 last_success는 현재 단일 값이므로 장비별 딕셔너리로 변경해야 합니다.

### 한 가지 확인

**R00012, R00047, R00048 세 장비에 동일한 CF 모델과 LSTM 모델을 사용하시겠습니까?**

② **장비별 모델 사용:** 각 장비의 데이터로 학습한 별도 CF·LSTM 모델 적용
